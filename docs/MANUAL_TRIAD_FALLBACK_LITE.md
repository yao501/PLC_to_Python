# 人工多 Agent 轻量备用流程

> 状态：`FALLBACK_LITE_REVIEW_CLOSED_PENDING_GIT`（`WP-20260806-078` 已完成 Claude 正式回审、Codex 独立审核与用户关闭；文件仍未跟踪/未提交/未合并）。这是 Claude 因配额或临时服务故障不可用时的手工备用流程，不替代项目正式 Claude 实施—Codex 审核协议。手册本身关闭不改变未来每个备用候选的失败关闭要求：候选正式轴仍须保持 `BLOCKED / user / user` 直到完成 Claude 回审、Codex 独立审核和用户关闭。
> **性质声明**：本文件是**人和 Agent 的协作规范与证据约束**，不是运行时产品功能。它不声称在技术上能强制任何模型遵守，也不提供任何无人值守或自动安全保证；启用、写入权、分级、审核与关闭仍由主控和用户按本规范人工裁决。

## 1. 何时启用

仅在正常实施方因已确认的配额、认证、代理或短期服务故障不可用，且用户已授权继续当前项目时启用。心跳缺失、协调器停止、任务困难或“希望更快”本身都不是启用权。

每个备用包必须显式记录：

- `fallback_protocol: MANUAL_TRIAD_FALLBACK_LITE_V1`
- `fallback_requires_claude_reaudit: true`
- `fallback_formal_baseline_eligible: false`
- 正式 `status / owner / handoff_to` 继续失败关闭为 `BLOCKED / user / user`。

## 2. 先分级，再决定角色

| 等级 | 特征 | 默认组合 |
|---|---|---|
| C0 | 单处文字/常量/兼容性修正，不改语义 | 主控直接实施 + 定向复核；常驻角色池不必唤醒 |
| C1 | 1–5 文件、边界明确、可用单元测试锁定 | 主控规划 + Delivery；Reviewer 按风险定向复核 |
| C2 | 跨组件、安全链、事务/状态机或不明确规格 | Planner + Delivery + Reviewer 全部参与 |
| C3 | 新子系统、外部进程、持久化、并发恢复或无人值守 | 默认停止，拆为独立产品/项目后再授权 |

可以保留 Planner、Delivery、Reviewer 三个常驻角色身份，以便复用已经形成的项目上下文；“常驻”只表示角色可继续被唤醒，不表示持续运行、每包都参与或取得写入权。主控按 C0–C3 只唤醒需要的角色：Planner 和 Reviewer 优先使用高能力模型，Delivery 依交付复杂度选择足够但不过量的模型。

### 默认模型路由

| 角色 | 默认模型与推理等级 | 允许降级/升级 | 必须记录 |
|---|---|---|---|
| 主控 | C2/高风险任务优先 `gpt-5.6-sol / xhigh` | C0/C1 可按任务降为 `high`；当前会话模型不可运行中切换时如实沿用 | 实际模型、推理等级、调整理由 |
| Planner | `gpt-5.6-sol / high` | 不可用时可降为 `gpt-5.6-terra / high` | 实际模型、推理等级、是否新鲜上下文 |
| Delivery | `gpt-5.6-terra / high` | 机械、低风险且验收完全确定的 C0/C1 任务才可降为 `medium` | 实际模型、推理等级、唯一 writer 身份、降级理由 |
| Reviewer | `gpt-5.6-sol / high` | 不可用时可降为 `gpt-5.6-terra / high` | 实际模型、推理等级、是否新鲜上下文、写入为零 |

模型等级只影响资源路由，不改变角色权限、验收标准或正式状态。可靠性优先于节省额度，但高等级模型不能替代 scope、测试和独立审核。主控可依据 C0–C3、状态机/事务/安全影响、文件规模和验收确定性调整配置；实际模型与默认值不一致时必须写明理由，不能把期望配置冒充执行事实。

### 三个角色的固定职责

- **Planner（只读）**：把用户目标转换为 scope、依赖、验收、测试层级、风险和停笔条件；不写产品文件，不为展示完整而主动扩大任务。
- **Delivery（唯一 writer）**：只在冻结 scope 内实施；先证明真实缺口，再完成最小完整修复和直接回归；发现规格歧义或必须扩 scope 时停笔报告。
- **Reviewer（只读）**：复算交付哈希，按验收逐项核对，并对接口、状态、失败关闭和相邻回归做与风险相称的未预告反证；不得把个人偏好的新功能或无限威胁模型包装成当前包缺陷。
- **主控**：负责分级、唤醒与停用角色、维护唯一 writer、裁决测试层级，并识别任务是否已偏离产品目标。用户仍是最终仲裁方。

### 每次唤醒前的最小必读集

每个被唤醒角色先完整读取本规范，再按角色只读：`CODEX_GUIDE.md`、当前工作包、当前 scope 清单、scope 直接依赖的权威规格、源码和测试。不得默认通读完整 handoff 历史、全部风险表、全仓源码或全套测试；只有阶段总验收、跨仓影响调查或当前证据明确指向范围外时，才由主控书面扩大读取范围。

常驻上下文只是导航缓存，不是权威事实。每次唤醒必须重新核验项目根目录、当前分支/HEAD、工作区、当前工作包五字段、scope manifest 和是否已有 writer；发现文件、哈希或状态与任务描述不一致时先停止，不凭旧记忆继续。跨项目复用时必须建立新项目简报和权威文件清单，不得继承本项目的规格、风险结论、测试命令、Git 权限或 PLC 假设。

C2 的 Planner 与 Reviewer 默认使用该工作包的新鲜 Agent 上下文；“角色常驻”不等于复用同一个长上下文。确需复用时，启动任务的第一项可检查产物必须明确：丢弃哪些旧的未交付结果、当前角色、当前工作包、当前权威基线以及下一项必交产物。主控只下发当前包的最小 docket 和相关条款，不让 Agent 通过完整 handoff 历史重建任务。

### C2 Planner 开工卡硬门禁

Delivery 启动前，Planner 必须先交付一页可检查开工卡，至少包含：

- 精确 scope 与冻结依赖；
- 将新增或改变的 API/数据合同；
- 每条验收要求到实现位置和测试的映射；
- 计划覆盖的失败/反证清单；
- 定向测试、静态检查和最终功能完整组命令；
- 停笔、扩 scope 和重新规划条件。

开工卡缺任一项、仍是开放式分析或混入旧工作包内容时，主控不得启动 Delivery。该门禁检查的是最小可实施性，不要求 Planner 预先设计全部实现细节。

## 3. 写入权与交接

1. 主控冻结 scope、baseline manifest/聚合哈希、验收和排除项。
2. 同一时间只有一个 scope writer；Planner/Reviewer 只读。
3. Delivery 先做能证明缺陷的最小红灯，再实施最小修复，最后冻结 manifest。
4. Reviewer 先复算同一哈希，再审差异和未预告反证；审核期 writer 停笔。
5. 任何通过只能记为 `PROVISIONALLY_APPROVED_PENDING_CLAUDE_REAUDIT`，不得自动更新正式轴、关闭、Git 或 GitHub。

每个工作包都必须完成一张小型验收映射：目标或风险点 → 实现位置 → 定向测试/检查 → 未验证边界。文件少不等于可以省略接口、默认值、跨拍状态、双实例隔离、错误路径或失败原子性；只检查与本包实际行为有关的项目，不为凑表扩展范围。

为降低确认偏差，Reviewer 先只根据工作包合同、权威规格和冻结差异形成自己的检查清单，再读取 Delivery 的自审与测试说明。审核发现必须分类：

- **当前包阻塞缺陷**：违反本包验收、造成由本包引入/改变的回归，或使本包依赖的安全边界失效；给出可复现证据并按 P1/P2 返修。
- **相邻既存风险**：真实但不是本包引入、也不阻止本包独立成立；登记风险或后续工作包，不自动扩当前 scope。若本包必须依赖该风险才能安全成立，则升级为阻塞依赖。
- **改进建议**：可读性、通用化或尚无失败证据的增强；进入 backlog，不得冒充 P1/P2。

Reviewer 的未预告反证应覆盖可达公开输入和当前威胁模型；若要扩大到新的攻击者能力、输入语法或产品功能，先说明现实可达性和对当前验收的影响，由主控决定是否升级范围。

Reviewer 的盲审顺序是机械门禁：①复算冻结哈希；②只依据合同、规格和差异形成独立检查清单；③完成第一遍静态审查；④再读取 Delivery 自审和主控的具体怀疑点；⑤补充未预告反证并给结论。主控怀疑点只能作为第二遍补充，不能替代 Reviewer 自己的检查清单。

## 4. 测试与审查分层，不每包重复全仓

- **包内迭代**：只运行能杀死当前缺陷的定向反证和直接受影响回归；修改对应测试后必须证明新测试在修复前确实能失败，或说明无法红灯的原因。
- **工作包交付门禁**：在最终冻结候选上运行一次“功能完整组”，覆盖验收映射、公开接口、状态与错误路径、直接相邻回归、静态检查和 scope 哈希；默认不运行全仓。
- **工作包审核**：优先审差异、验收映射、哈希、未预告反证和高风险路径。Reviewer 独立运行定向反证和静态门禁，可引用同一哈希上的 Delivery 回归证据，但不得只看测试数字就通过。
- **批次回归**：完成一组相关工作包（建议 3–5 个）、修改共享运行时核心或准备 Git/GitHub 收尾时，由主控安排一次扩展回归；范围覆盖该批次的依赖链和既有关键安全路径。
- **阶段总验收**：完成路线中的大阶段时，单独建立验收包，对全仓结构、权威规范、该阶段全部变更和关键执行路径做系统复核，并运行正式、prototype、全仓及该阶段规定的完整测试。该结果形成新的阶段快照，不回写历史工作包数字。
- 只有产品 scope 或冻结候选哈希改变时才重跑相应门禁；控制记录追加不得冒充产品 scope 漂移。若依赖、解释器版本或共享公共接口发生变化，主控可以提前升级到批次回归。

阶段总验收也不要求三个角色逐字重复阅读同一批文件：Planner 核对路线、规格与覆盖清单，Reviewer 系统审查冻结差异和关键执行路径，Delivery 只在审核产生已裁决返修后恢复写入；主控汇总三类互补证据并运行一次完整测试组。

## 5. 防止过度设计的升级门槛

任一条命中时，先暂停 writer、冻结当前证据，由主控报告并进入重新规划闸门：

- 原定 C0/C1 超过 5 个文件、300 行净变更或 60 分钟；
- 同一缺陷簇已经返修 2 轮仍新增 P1，或审核开始持续扩大输入语法/威胁模型；
- 需要新的持久化、外部进程、lease、DAG、API、Dashboard、自动崩溃恢复或无人值守；
- 为保持宽松输入而需不断扩展复杂防御，而收紧规范输入能更直接地解决问题；
- 工作包变成独立平台或新产品。

重新规划不是放弃漏洞。主控必须先区分根因属于局部实现遗漏、规格/输入合同缺陷、架构不适配、测试盲区还是审核范围发散，再记录新的决策：

1. 根因单一且仍能在原 scope 内完整修复：保留同包，修正方案后继续；
2. 连续补丁已经互相牵制：停止补丁式返修，改为有不变量和迁移测试支撑的局部重构；
3. 根因跨越多个独立责任：拆成有明确依赖顺序的窄包，但原 P1 保持阻塞直至承接包实质关闭；
4. 规格或现场语义无法裁决：交用户或目标 PLC 证据裁决，不猜测实现；
5. Reviewer 扩大了未经授权的产品范围：收回到工作包合同，同时把确有价值的新风险登记为后续候选。

未解决的 P1 不得通过、关闭或 Git/GitHub 收尾。`max_rounds=5` 是失败关闭上限，不是必须用完的预算；重新规划后可以继续修复，但不能只靠增加轮次维持进度假象。

### 执行预算与可见停表

- 每次唤醒只下发一个有明确输入、输出物、scope、验证命令和停止条件的任务；不得让三个角色并行回答同一个开放问题。
- 主控在开工时记录复杂度、预计文件数和测试层级；实际规模超过预计一倍或 C0/C1 超过 60 分钟时，立即停表并重新分级。
- C2 默认使用状态型检查点，而不是把一次等待调用当执行期限：5 分钟应出现 Planner 最小开工卡，15 分钟应出现 Delivery 红灯或经证据确认的真实缺口，30 分钟应出现冻结候选、测试结果和 manifest；复杂包可以由主控在开工卡中书面调整，但必须保留可检查产物。
- `wait_agent` 超时只表示控制权返回主控，不表示 Agent 执行超时，也不授权中断。只有 scope/权限漂移、明确工具故障、错误工作包、超过书面检查点仍无任何可检查产物，或用户要求停止时，主控才可中断并记录原因。
- Agent 完成任务后保持空闲，不做心跳式重复读取、轮询或自行寻找下一任务；后续唤醒只汇报相对上个冻结点的增量。
- 配额接近耗尽时优先保全 manifest、测试结果、未完成项和下一精确动作；不得为了“用完本轮”开启新的功能或全仓检查。

### 同包里程碑与 FINAL 机械门禁

C2 工作包默认分三个内部里程碑，不为每个里程碑另建工作包：

- A：核心 API、数据合同和最小接受路径；
- B：完整失败矩阵、失败关闭、原子性/隔离及直接相邻回归；
- C：冻结 manifest、功能完整测试和交接证据。

B 未完成时，A 只能报告为中间候选，不能称为完整交付。Agent 只有在以下项目全部存在时才能发送 `FINAL=COMPLETE`：验收映射逐项结论、指定测试的真实命令和精确计数、逐文件 manifest 与聚合哈希、适用 Python 文件的 `py_compile`、`git diff --check`、未验证边界和停笔项。未满足时只能发送 `CHECKPOINT/INCOMPLETE`，并明确下一动作。

Delivery 第一次提前发送完成结论时，主控允许同一 writer 受控续作一次，并列明缺失门禁；第二次仍提前结束，则冻结已有产物、停止复用该 writer，并更换 Delivery 或由主控显式接管。两次事件都必须保留在工作包记录中，不得靠连续唤醒把不完整交付包装成完成。

## 6. 必填证据与 Claude 回审队列

每个候选至少保存：

- 工作包 ID、复杂度等级、单一 writer 与 Reviewer 身份；
- baseline / delivery / review-start / review-finish 聚合哈希和逐文件 manifest；
- 首次失败、根因、最小修复、真实测试命令/计数、未验证边界；
- P1/P2、scope drift、审核方写入是否为零；
- `fallback_requires_claude_reaudit=true` 与正式轴 `BLOCKED/user/user`。

Claude 恢复后按依赖顺序审核候选，而不是按文件数量重做全部开发：先复算冻结 manifest，再审差异和已记录反证，可在 scope 内修正不合理处并交给新 Codex 独立审核。只有该正式链通过后，用户才能决定 CLOSED 与 Git/GitHub 收尾。

## 7. 始终排除

备用流程不会放大任务授权，不会触碰项目外文件，不会自动 Git/GitHub 写入，不会把 Python 测试升级为 PLC/CODESYS、HAL、硬件 watchdog 或现场安全证明。遇到规格歧义、扩 scope、破坏性操作、外部系统或现场边界不明时，必须停止并交用户裁决。

本规范只约束协作行为与证据留痕，**不构成对任何模型的技术强制，也不提供无人值守运行保证**；它靠主控和用户按本文件人工执行，而非靠工具自动阻止违规。任何“备用 Reviewer 已通过”都只是候选证据，正式产物仍须经 Claude 回审、Codex 独立审核和用户关闭。
