> 本文件是项目从"功能块迁移"走向"Python 原生软 PLC 平台"的**统一指导文档**。

## 0. 愿景与定位

### 0.1 我们到底在做什么

不是"把某一个 PLC 程序翻译成 Python"，而是**做一个 Python 原生的软 PLC 平台**：

- 支持用 **ST 和 CFC** 两种方式编程（与 CODESYS 中常用方式对齐）；
- 已迁移的功能块（14 个业务块 + 8 个原语）是这个平台的**标准库元件**；
- 平台具备 **实例化功能块 → 连线 → GVL 全局量 → 按扫描周期执行** 的通用能力；
- 最终能像 CODESYS 那样"新建 POU、写 ST 或拖 CFC、下载运行"。

### 0.2 为什么要做（核心动机）

让控制逻辑成为**普通的 Python 代码**，从而天然地与 AI 算法、Python 数据程序运行在**同一平台、同一生态**里——而不是"控制在 CODESYS、AI 在 Python"两套平台来回倒数据那样割裂。这是本平台区别于商业软 PLC 的根本价值，也是所有设计取舍的最终依据：**控制 + AI 一体化运行**。（架构上控制运行时与重 AI 推理**分进程**隔离 + 共享内存/IPC，见 D-AI 与阶段 9——"一体化"指平台/生态/数据一体，不是同一 OS 进程。）

### 0.3 定位与范围边界（Non-Goals）

- **不是** CODESYS 的完整克隆；
- 第一阶段**只支持 ST + CFC** 两种语言，不做 LD / IL / SFC；
- 任务模型按当前工程：**单任务、固定 500ms**（多任务/多周期不在首版范围，留作后续扩展点）；
- 授权停在阶段一（一机一码）；离线签名/公私钥属授权阶段二，按需启动；
- 图形编辑器是语言前端的**最后一环**，不提前做。

### 0.4 设计北极星（贯穿全文的不变式）

> **一个程序模型（IR）+ 一个扫描引擎；ST 与 CFC 都是它的前端；安全是平台服务。**

任何程序——无论用 ST 写、用 CFC 画、还是从 CODESYS 导入——最终都编译成同一种内部形态：
**一组功能块实例 + 一个语言无关的可执行 IR 指令列表 + 一个变量空间**（`IR_SPEC §5`），由引擎按 `00a` 五步式每拍推进一次。
这条不变式把"4 种编程入口 × 2 种执行模型"的组合爆炸，收敛成"1 个 IR + 1 个引擎 + 若干可独立开发的转换器"。

### 1.1 一拍执行时序（引擎核心，泛化自 `00a` 五步式）

```
每个扫描周期（固定 500ms）：
  1. 输入映像锁存   —— 一次性采样所有物理/逻辑输入到输入映像
  2.+3. 执行可执行 IR —— 逐条执行指令列表（块推进与连接解算已编译进指令序）
  4. 输出安全策略   —— 每个物理输出按其 OutputPolicy 生成最终值（分类型、分故障原因，非布尔 AND）
  5. 一次性提交     —— 输出映像集中写出（shadow 模式下只算不写）
```

精确定义见 `ENGINE_SCAN_SPEC §3/§4`。ST 与 CFC 的差异只体现在"指令顺序怎么来"（lowering 期，见 `IR_SPEC §6`）：
- **ST** → 顺序就是代码书写顺序（显式顺序）；
- **CFC** → **导入的图按载体分支**（D3 v2.2.2 裁决，见 `ENGINE_SCAN_SPEC §5.1`）：PLCopen XML 显式带每元素 `executionOrderId`，原样保留；.export 自动数据流模式不存原始序号，执行序须导入器**重建**（算法未冻结，重建前拒绝生成可执行 IR）；**新建的图**用拓扑排序定序。反馈起点读"上一拍值"（`LOAD_PREV`，映射待真机样本验证）。

两者在**加载期**就统一成"同一种可执行指令列表"，引擎运行期对两者一视同仁。

## 3. 分阶段计划

> 记号：每阶段给出 **目标 / 范围 / 关键产出 / 依赖 / 验收标准 / 主要风险**。
> 优先级原则：**MVP 优先，逐层验收，闸门通过再进下一层**。

### 阶段 0 — 设计基线（地基，先于任何编码）

- **目标**：在写引擎第一行代码前，锁定平台地基的几份核心规格，避免后期返工。
- **范围**：
  - IR 数据模型（实例 / 连接 / GVL / RETAIN 属性 / I/O 映射 / 执行顺序）的字段定义；
  - 引擎一拍时序规格（即 §1.1 的精确化，含管脚求值与连接解算细则）；
  - L2 组件契约：FB 基类接口、管脚/类型元数据格式、库注册方式；
  - **类型系统决策**：REAL 用 32 位仿真还是沿用 Python 64 位 float（影响长跑保真，见 §6）；
  - 反馈环（CFC 回路）"取上一拍值"的统一规则。
- **关键产出**：`docs/IR_SPEC.md`、`docs/ENGINE_SCAN_SPEC.md`、`docs/COMPONENT_CONTRACT.md`；更新 `.cursor/rules`。
- **依赖**：无。
- **验收**：设计稿评审通过；能用纸面走通一个最小程序的一拍数据流。
- **风险**：IR 设计不足会污染所有上层——此阶段"多花一天省一个月"。

### 阶段 0.5 — 语义基线修订（进阶段 1 前的工程冻结闸门）

> 由外部评审（ChatGPT5.5）反馈引入。阶段 0 定位修正为**概念设计完成**；进入正式编码前，需把"改起来代价大"的地基语义夯成可冻结的工程基线。**纪律：0.5 只冻结贵的语义，其余"模型先定、实现后延"，避免膨胀成造平台。**

- **目标**：把阶段 0 的概念设计升级为可冻结的工程语义基线。
- **范围（10 项，按"必须冻结 / 模型先定可后延"分级）**：
  1. **【冻结】目标环境画像 + 一致性等级**：锁定 CODESYS **SP16.1** / CPU·OS / 编译选项 / 库版本 / 任务配置 / CFC 顺序模式 / I/O 驱动；定义"**容差等价**"与"**位级等价**"两档一致性等级。
  2. **【冻结】源模型 与 可执行 IR 分离**：ST AST、CFC 图作为前端源模型；新增语言无关可执行 IR（Load / Store / CallFB / Convert / Jump 等），ST 与 CFC 都 lower 到它（可先最小指令集）。
  3. **【冻结】分类型输出安全策略**：每个输出定义 `OutputPolicy`（类型 / 安全值 / 失联策略 / 限速 / 联锁 / 是否保持），替换只适用 BOOL 的 `req AND system_ready AND ...`。
  4. **【冻结】CFC 顺序/反馈规则（D3 v2.2.2 载体分支裁决）**：按载体能提供什么保留什么——PLCopen XML 显式带 `executionOrderId`，原样保留（含来源标识）；.export 自动数据流模式不存原始序号，只保留顺序模式/拓扑/连线/`IsFeedbackStart`，执行序须重建（算法本次不冻结，未就绪时拒绝生成可执行 IR），**不得表述为"保留原始序号"**；拓扑推断仅用于**平台通用的新建图定序**，不用于改写载体已显式提供的顺序，`.export` 自动模式的顺序重建另属阶段 5 导入器重建算法。
  5. **【冻结】REAL/整数语义模式（修订 D4/D5）**：定义 `fidelity`（REAL32 / LREAL64、按目标位宽仿真整数回绕）与 `engineering`（Python float + 容差）两档；明确"块源码零改动"只能给到 `engineering`，位级保真需块级 float32 工作量。
  6. **【冻结】早期真 PLC 黄金轨迹（最小集）**：现在就抓第一批基准轨迹（至少 TON / 边沿 / 反馈环 / REAL 递推 / 冷·热启动），不等阶段 6。
  7. **【模型先定】POU 模型扩展**：支持用户自定义 `FUNCTION_BLOCK` / `FUNCTION`、`VAR_TEMP`、`VAR_IN_OUT` 别名、实例内存、调用帧。
  8. **【模型先定】RETAIN/PERSISTENT 模型加厚**：冷/热/下载语义差异、FB 级 retain 传播；实现仍在阶段 8。
  9. **【模型先定】AI 进程隔离**：控制运行时与 AI worker **分进程** + 共享内存/IPC，同一平台体验；修正"同进程"表述。
  10. **【治理】对齐**：阶段验收勾选状态与风险状态一致。
- **0.5 可执行验证原型（本阶段内完成，消除与阶段 1 的循环依赖）**：一次性最小原型（可丢弃代码，不是阶段 1 交付物），覆盖：`LOAD_CONST`/`LOAD_VAR`/`STORE_VAR`/`BINOP AND`/`JMP*`、TON 一个库块经描述符调用、一个 BOOL 输出走 `OutputPolicy`；同一逻辑 ST 与 CFC 两条 lowering 路径产出同一指令列表并跑通 N 拍。**另须包含 4 个语义敏感案例**（二轮评审要求，防止把未定准语义固化进实现）：① 一个整数临时位宽/存储截断案例（验证 `int_intermediate_policy` 两种策略可切换且结果不同，`IR_SPEC §5.4`）；② 一个 REAL/F1 量化案例（F1-expr 与 E 结果可区分）；③ 一个 `VAR_IN_OUT` 引用案例（`ValueRef` 别名语义，写透到调用方）；④ shadow / 扫描异常 / 提交失败三条输出路径案例（`ENGINE_SCAN_SPEC §4.1/4.3/4.4`）；⑤ **两份同类型 FB 实例状态互不串扰**案例（验证定义/实例分离，`IR_SPEC §3`）。**目的仅是证明"IR 语义可执行、双前端可合流、关键语义可测"**，从而支撑冻结评审；正式工程化实现全部放阶段 1。

### 阶段 1 — 执行引擎内核 MVP（headless）

- **目标**：一个无界面引擎，能加载内存里的 IR、正确推进扫描、带安全包壳。
- **范围**：
  - L2：FB 基类 + 库注册表；给现有 14 块 + 8 原语补管脚/类型元数据；
  - L3：IR 内存模型（先由 Python 代码内部构造，作为引擎自测手段，**非最终用户入口**）；
  - L4：变量空间 + 过程映像 + 连接解算 + **显式顺序**执行 + 五步式扫描循环；
  - L5：安全服务（system_ready / 输出门控链 / startup_inhibit / watchdog / 安全默认值 / shadow mode）；参数装载校验层 `RUNTIME-PARAM-VALIDATION`（归并现有 `check_pt_ms` / `check_tb_sample_n_integer`，启动期硬拦截）。
- **关键产出**：`src/runtime/` 引擎（正式工程化实现全部内核，0.5 原型代码不复用即弃）；标准库元数据；一个手搭的最小程序跑通。
- **依赖**：**阶段 0.5（冻结闸门通过）**。
- **验收**：最小程序（如 TON + 逻辑）确定性跑 N 拍；安全门控 / shadow / 启动抑制 / 参数非法硬停 / OutputPolicy 分原因故障策略（`ENGINE_SCAN_SPEC §4`）均有测试。
- **风险**：把"引擎内部 Python 构造法"误当成最终编程入口对外暴露——必须明确它只是内部/测试用。
- **当前状态（Python 单任务装配子范围已审核关闭，待 Git/GitHub 收尾）**：阶段 1 内核（L2 元数据 / L3 IR / L4 五步引擎 / L5 安全服务 + 参数校验）与“手搭最小程序跑通”验收已有 Python 实现。`WP-20260730-050 CLOSED`（承接已封存的 WP-049 检查点）新增 `src/runtime/task_runtime.py::build_task_runtime` / `TaskRuntimeAssembly`，把内核连成**同一对象图**并以手搭 TON（`Motor=TON.Q AND NOT Stop`、`cycle_ms=500`）跑通默认 shadow 冷启动 / N 拍确定性 / 显式实写恰一次提交 / monitor 一次性派发 / scan·commit fault 分层的 E2E（`tests/test_runtime_task_runtime.py` 23 条）；Codex Round 3 `APPROVED`，当前尚未提交/合并。该结论不代表阶段 1 全面关闭——真实调度 / 多任务 / startup inhibit 计时与释放 / 外部信号源 / HAL / CFC 定序 / CODESYS 对拍仍未实现。**下一步**：Git/GitHub 收尾 → 阶段 2 CFC 定序编译器。

### 阶段 2 — 数据流定序编译器（CFC 执行语义的运行时基础）

- **目标**：引擎能加载"连线图"并正确定序执行——这是 CFC 的运行时底座（先于任何画图界面）。
- **范围**（按 D3 v2.2.2 载体分支裁决）：导入的 CFC **按载体分支定序**（`ENGINE_SCAN_SPEC §5.1`）——PLCopen XML 用已保存的 `executionOrderId`；.export 自动模式待重建算法（阶段 5），未就绪拒绝生成可执行 IR；反馈起点 lower 成 `LOAD_PREV`（读上一拍）；拓扑排序**仅用于平台通用的新建图定序**（无环拓扑定序，有环由用户标反馈起点打破；不改写载体显式顺序，`.export` 自动模式重建另走阶段 5 导入器算法）；CFC 模型加载器（框/管脚/连线/顺序字段（含 `order_source`/`carrier`）/反馈标记作为数据）。
- **关键产出**：顺序编译器；CFC 模型 loader。
- **依赖**：阶段 1。
- **验收**：同一程序用"连线图"表达，结果与"显式顺序"逐值一致；含反馈环的回路按 PLC 上一拍语义正确。
- **风险**：反馈环/执行序边界条件，需要充足用例。

### 阶段 3 — ST 语言前端

- **目标**：能像 CODESYS 一样用 ST 写 POU，平台每拍解析并执行。
- **范围**：
  - ST 词法 + 语法（子集）：`VAR` 声明、赋值、`IF/CASE/FOR/WHILE`、FB 实例调用、表达式、IEC 运算符与类型、`T#`/`REAL` 字面量、`SEL/MIN/MAX/ABS/LIMIT` 等标准函数；
  - 绑定到标准库 FB 实例与 GVL，在扫描内执行；
  - **关键决策**：解释执行 vs 编译成 Python（性能 / 调试 / 实现成本权衡）。
- **关键产出**：ST 前端 + 一致性测试套件。
- **依赖**：阶段 1（语言落到 IR/引擎上）。
- **验收**：一段代表性 ST POU 正确运行；理想情况下，用 ST 重写某个已迁移块的源 ST，结果与该块 Python 实现一致（自我印证）。
- **风险**：ST 语义细节（如 `SEL` 极性、整数/实数提升、`TIME` 字面量）易错——直接复用迁移阶段沉淀的 `compat` 与对 `SEL` 等的既有理解。

### 阶段 4 — CFC 模型 + 图形编辑器

- **目标**：能图形化拖拽功能块、连线、设执行顺序；编辑器产出阶段 2 能执行的 CFC 模型。
- **范围**：CFC 数据模型（框/管脚/连线/顺序号/注释）+ 编辑器界面（建议 Web 技术，便于与 Python 生态/浏览器结合）+ 存取往返 + 接标准库。
- **关键产出**：CFC 编辑器应用；模型序列化格式。
- **依赖**：阶段 2（运行时底座）、阶段 1（标准库元数据）。
- **验收**：在编辑器里搭一个 CFC 程序，引擎跑通，与等价 ST 结果一致。
- **风险**：UI 工程量大；必须建在**稳定的 IR / CFC 模型**之上，否则反复返工——故排在语言工作的最后。

### 阶段 5 — CODESYS 工程导入

- **目标**：解析现有 CODESYS 工程（`.export` / XML）的 ST/CFC，转成 IR，让既有程序（含真实 `PLC_PRG`）直接跑。
- **范围**：导入解析器；CODESYS 标准库调用 → 本平台标准库的映射表；GVL 导入。
- **关键产出**：导入器；映射表。
- **依赖**：阶段 2 + 阶段 3（CFC 与 ST 两种来源都要能进 IR）。
- **验收**：导入真实工程的 `PLC_PRG`，能加载并运行（此时它从"待迁移目标"正式变成"平台验收用例"）。
- **风险**：CODESYS 导出格式版本差异；非标准库调用的覆盖度。

### 阶段 6 — 对拍 / 黄金轨迹验证（接现场前的命门）

- **目标**：逐值证明 Python 平台复刻真软 PLC 的行为。
- **范围**：
  - 在真软 PLC 上抓取输入/输出/关键中间量的时间轨迹；
  - 回放进 Python 平台，按容差断言等价；
  - 落实 REAL 32 位保真决策（见 §6）；
  - 裁决掉 `RISKS.md` 里所有"未真机验证"项（BLINK 时序等）；
  - 长跑积算类（HSACCUM / STATISTICS）漂移核查。
- **关键产出**：共仿/回放框架；黄金轨迹集；保真报告。
- **依赖**：阶段 5（或至少阶段 2/3 能跑参考程序）。
- **验收**：选定参考程序在代表性工况下与真 PLC 一致。
- **风险**：轨迹采集的时钟对齐与采样精度；**此阶段必须早于接现场**。

### 阶段 7 — I/O、HAL 与实时运行（接现场，全是 blocker）

- **目标**：在真实硬件上、按实时节拍、安全地驱动现场 I/O。
- **范围**：
  - HAL：I/O 驱动/协议（按部署定，如 Modbus / OPC-UA / 现场总线）；
  - I/O 映像映射（GVL ↔ 物理点位/地址）；
  - 实时扫描驱动（定时循环、抖动/超时处理、watchdog 升级响应）；
  - **首接设备先 shadow mode 只读不写**，对拍通过后才放开写；故障落安全默认值。
- **关键产出**：HAL + 驱动；I/O 映射配置；实时循环；部署手册（runbook）。
- **依赖**：阶段 6（对拍通过）。
- **验收**：shadow 模式对着真实 I/O 跑符合预期；受控放开写；安全态可靠触发。
- **风险**：实时性与抖动；现场安全——**安全优先级最高**。

### 阶段 8 — 持久化（RETAIN / PERSISTENT）

- **目标**：断电/重启后恢复保持型变量。
- **范围**：IR 中变量的 RETAIN/PERSISTENT 属性；快照/恢复；存储介质；冷启动 vs 热启动初始化语义。
- **关键产出**：持久化机制 + 恢复钩子。
- **依赖**：阶段 1（IR 变量属性）；接现场前需就位，可与阶段 7 并行。
- **验收**：杀进程+重启后保持态正确恢复；冷启动正确按初值。
- **风险**：与扫描时序的一致性（何时快照）；建议正式登记进 `RISKS.md`（目前未跟踪）。

### 阶段 9 — AI / Python 集成层（平台的核心价值兑现）

- **目标**：让控制逻辑与 AI/Python 程序在同一平台一等公民地协作（控制运行时与 AI worker **分进程** + 共享内存/IPC，D-AI）——这是做整个平台的根本动机。
- **范围**：
  - **AI 功能块适配器**：把一个 Python/ML 模型包装成一个 FB，在扫描内被调用，带延迟与安全边界；
  - **数据总线**：控制变量与异步 AI/分析程序共享（特征导出供训练、推荐回灌等）；
  - **"AI 建议、PLC 把关"范式**：AI 输出走"建议 vs 命令"分离，由安全门控决定是否采纳——可直接复用 **APCM/APARA 的人工确认应用按钮模式**作为模板；
  - **确定性/时序隔离**：重 AI 推理放在**扫描进程之外**（分进程异步），结果经共享内存/IPC 锁存进扫描，保证扫描周期不被拖垮；
  - 日志/特征导出，闭环到模型训练。
- **关键产出**：AI-FB 适配器；数据桥；参考样例（如一个 ML 设定值顾问，经门控应用模式喂给 APCM）。
- **依赖**：阶段 1（引擎 + FB 契约即可起步，**可早于现场阶段并行预研**）。
- **验收**：一个 AI 模型（独立 worker 进程）与控制回路在同平台协作运行，AI 输出经共享内存/IPC 锁存，在安全门控下被控制逻辑安全消费。
- **风险**：AI 推理时延破坏扫描确定性——靠时序隔离与门控解决。

### 阶段 10 — 授权阶段二（按商业需要）

- **目标**：离线签名 / 公私钥 / License 文件（`LIC-PHASE2-1`）。
- **依赖**：商业化决策；不阻塞技术主线。

## 6. 需要尽早锁定的关键设计决策

1. **REAL/整数数值语义**：✅ 已定（D4/D5 双模式：E 默认 / F1-expr+F1-boundary / F2 位级保真候选，`TARGET_PROFILE §4`）；**待真机裁决**：整数回绕发生点 `int_intermediate_policy`、REAL 中间精度、F2 是否立项 → 阶段 6 黄金轨迹验证。
2. **ST 执行方式**：解释 vs 编译成 Python（性能/调试/成本）。→ 阶段 3 定。
3. **CFC 编辑器技术栈**：Web vs 桌面（建议 Web，贴 Python 生态）。→ 阶段 4 定。
4. **实时循环驱动**：定时方式、超时/抖动策略、watchdog 升级动作。→ 阶段 7 定。
5. **现场 I/O 协议**：随部署环境定（Modbus / OPC-UA / 总线）。→ 阶段 7 定。
6. **AI 与扫描的确定性边界**：重推理如何离扫描线程、结果如何锁存。→ 阶段 9 定。
