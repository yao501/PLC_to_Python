## 1. 为什么需要这份画像

"完美复刻"必须先限定复刻对象。REAL 运算、整数溢出、类型转换的结果依赖目标系统的数值语义。本画像锁定目标系统，并把"复刻到什么程度"显式分级，避免"按需处理"式的模糊。

## 3. 数值语义基线（多数由 IEC 61131-3 + IEEE 754 标准确定，不依赖 CPU）

| 类型 | 位宽 / 表示 | 溢出/舍入（存储表示层） |
|---|---|---|
| BOOL | 1 位 | — |
| BYTE/WORD/DWORD/LWORD | 8/16/32/64 位无符号 | **模 2ⁿ 回绕** |
| SINT/INT/DINT/LINT | 8/16/32/64 位有符号（二进制补码表示） | 溢出行为**待目标画像锁定**（首版假设模 2ⁿ 回绕，须真机验证） |
| USINT/UINT/UDINT/ULINT | 8/16/32/64 位无符号 | 模 2ⁿ 回绕 |
| **REAL** | **IEEE 754 binary32（单精度 32 位）** | 见下方中间精度提示 |
| LREAL | IEEE 754 binary64（双精度 64 位） | — |
| TIME | 32 位毫秒（`T#…`） | 项目内统一 `int ms`（`00a` R1） |

**中间运算精度/位宽提示（待真机裁决项）**：上表锁定的是**存储表示**；**运算中间结果**的位宽/精度依赖编译目标，不能从标准直接推出：

- **整数**：临时结果按目标设备**原生位宽**计算（x86/ARM32 ≥32 位、x64 =64 位），截断发生在赋值点（`WORD` 运算不必然每步按 16 位截断）。对应 IR 参数 `int_native_width: 32|64`（⬜ 待 CPU 锁定）+ `int_intermediate_policy`（`native_width`（默认假设）/ `declared_width`，见 `IR_SPEC §5.4`）+ `int_overflow_convert_policy`（越界转换行为，TBD），由黄金轨迹 #7 表达式变体差分用例裁决（`RISKS.md::PLATFORM-INT-WIDTH-1`）。
- **REAL**：中间精度**依赖编译目标，待目标画像确认**——可能是标准单/双精度（SSE 类），也可能存在扩展精度中间值（如 x87 路径），不预设结论。"REAL 表达式逐步按 32 位舍入"是首版假设，需阶段 6 真机对拍验证；裁决结果记入本画像并调整 fidelity 实现。

## 4. 一致性等级（核心）

定义三档，从松到严。模式选择由本画像决定，绑定 D4/D5。

| 等级 | 名称 | 数值实现 | 判定 | 与"块零改动"关系 | 用途 |
|---|---|---|---|---|---|
| **E** | 工程容差等价 | 全程 Python `float`(64位)，整数 `int` 不回绕 | `|Δ| ≤ 容差`（见 §5） | ✅ 兼容（块不改） | **默认开发/MVP 模式** |
| **F1** | **边界量化**（两子行为见 §4.2） | **F1-expr**：IR 表达式**逐指令** binary32 + 整数按 `IR_SPEC §5.4` 政策；**F1-boundary**：原生库块仅**管脚边界**量化，块内部仍 64 位 | 值**可按 binary32 编码**（表示层保证）；**不承诺**与 CODESYS 结果 bit-exact（见 §4.1）；对拍按 §5 容差 + 编码检查 | ✅ 兼容（块不改，IR 层加约束） | 接现场前提升 |
| **F2** | **位级保真候选** | 块级 `float32` 全程 + 整数全程回绕 | **候选** bit-exact：逐步 binary32 与目标一致是设计意图，**是否真达位级一致须真机黄金轨迹证明**，不是天然保证 | ❌ **互斥**（需块级 float32 改造） | 最高保真，按需立项 |

### 4.1 为什么 F1 不能承诺"边界位级一致"（双重舍入）

**F1-boundary**（原生库块）的计算路径是"块内 float64 中间计算 → 管脚边界一次舍入到 float32"；CODESYS 目标的路径是"每一步都按 float32 计算与舍入"。两者数学上**可产生不同的边界结果**（双重舍入 / 中间精度差异），例如多步乘加链中 float64 累积后一次舍入 ≠ 逐步 float32 舍入。**F1-expr**（IR 表达式）虽然逐指令 binary32，也仍受目标编译差异（FMA 合并、指令选择、求值顺序）影响。因此：

- **F1 承诺的是表示层**：值一定是合法 binary32 可编码值（消除"Python 64 位泄漏到边界"这类系统性偏差），使对拍误差显著缩小且可解释。
- **F1 不承诺行为层 bit-exact**。F1 的对拍判定 = §5 容差判定 + "值 binary32 可编码"检查。
- 真正的 bit-exact 只可能出自 **F2**，且**须真机证明**：F2 的逐步 float32 是否与目标编译产物一致，取决于目标编译器指令选择（FMA、向量化、x87 与否）与运行库——这正是 §2 目标 CPU/编译目标信息不可跳过的原因。

### 4.2 F1 的两种子行为（v1.2 显式命名，避免混称"边界量化"）

F1 模式下实际存在两种量化粒度，取决于代码跑在哪一层：

| 子行为 | 适用对象 | 量化粒度 |
|---|---|---|
| **F1-expr（表达式量化）** | 经 IR 执行的代码（ST/CFC lower 产物） | REAL 按指令边界量化（`IR_SPEC §5.3`）；整数按 `int_intermediate_policy` |
| **F1-boundary（边界量化）** | 原生 Python 库块（14 块 + 8 原语，零改动） | 只在**管脚边界**量化（输入注入/输出回收），块内部 float64 不受约束 |

同一程序里两者并存（IR 代码调库块）。对拍解释差异时必须区分是哪个子行为贡献的偏差；文档与测试命名一律用 `F1-expr`/`F1-boundary`，不再笼统写"F1 边界量化"。

**关键诚实点（D5 冲突的解法）**：F2 需要改块内部数值类型，与"14 块源码零改动"不可兼得。E/F1 可在零改动下达成（F1 靠可执行 IR 在边界量化，覆盖边界见 `IR_SPEC §5.3`）。是否上 F2 由阶段 6 黄金轨迹的漂移结果 + 现场精度需求决定，作为独立工作量立项。
